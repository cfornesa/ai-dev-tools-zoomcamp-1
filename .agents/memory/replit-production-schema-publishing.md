---
name: Replit production schema publishing
description: Keep Django migration commands confined to the development schema flow when publishing to Replit-managed PostgreSQL.
---

Do not run Django migrations against the production database in a Replit deployment build or application startup. Replit's Publish flow compares the development and production schemas, presents any required rename/destructive confirmations, then applies the selected production schema diff.

**Why:** A production table can exist through Replit's managed schema flow without the corresponding Django migration ledger entry. Running `manage.py migrate` during a later build can then fail on an already-existing relation and block publication.

**How to apply:** Keep development migrations in the post-merge/development setup flow. Deployment builds may install dependencies, run deployment checks, and compile assets, but must not mutate production schema. For production schema changes, verify development and re-publish through Replit's schema-diff UI.

**Confirmed live (2026-08-29), issue #238:** this warning's exact failure mode materialized. Production was missing `scenes_project3d`/`scenes_sceneversion3d` (migrations 0018/0019 never applied there). As a workaround, `RUN_MIGRATIONS_ON_START=true` (the escape hatch already built into `scripts/start.sh`) was set via Replit's Configurations panel and a Republish triggered. Result: the deployment candidate crash-looped and never came up —
`psycopg.errors.DuplicateTable: relation "scenes_mistralcredential" already exists` on migration `0016_mistralcredential` (added 2026-08-21, predating this incident by over a week). `scripts/start.sh` treats a failed migration as fatal, so the whole app failed to start, not just the one broken feature. The candidate was never promoted (Replit kept serving the last good revision throughout, so end users were unaffected), and the config was reverted (deleted) to clear the crash loop.

**This means the drift is not limited to 0018/0019** — production's actual schema and Django's `django_migrations` ledger have been diverging for a while (at least since 0016), almost certainly because tables were created through Replit's own schema-diff-and-apply flow without recording a matching ledger entry. `RUN_MIGRATIONS_ON_START` is **not safe to use as a blanket fix** while this ledger/schema mismatch exists anywhere earlier in the migration sequence than the one you're trying to fix — `manage.py migrate` applies migrations in order and will hit the first mismatch it finds, regardless of which one you actually wanted applied.

**How to apply (revised):** before ever setting `RUN_MIGRATIONS_ON_START=true` against this production database again, first reconcile the full migration history — compare every `scenes/migrations/*.py` file against both the production table list and `django_migrations`' actual row contents (not just the row count) to find every table that exists without a ledger entry, and use `manage.py migrate --fake <app> <migration>` (recording it as applied without running its SQL) for each one that already has its table, in the correct order, before relying on a real `migrate` run. This is delicate enough that it likely needs to be done manually/carefully by the repository owner (or an agent with direct production database access) rather than automated at container startup — the crash-loop risk otherwise isn't confined to one feature, it takes down the entire app.

**2026-09-17 confirmed recurrence, issue #598 — a `RunPython`-then-schema pair blocks every future `migrate` invocation, not just the one that hit it:** while working #589 (missing `scenes_project.seo_config`), a Shell command with `DATABASE_URL` overridden to Production failed immediately with `InconsistentMigrationHistory: Migration scenes.0061_scene_conversion_run is applied before its dependency scenes.0060_seed_snapshot_cadence_policy`. This is Django's `check_consistent_history`, which validates the *entire* recorded ledger unconditionally on every `migrate` call — including `--fake` and targeted ones — so a single such gap blocks all future migration commands against that database, not only the one that surfaces it. Direct inspection (sorted by `django_migrations.id`, i.e. insertion order) found the last `scenes` row ever inserted was `0062`; nothing from `0063` through `0078` (16 migrations) had a ledger row at all, yet at least one of those tables (`scenes_syncmutationreceipt`, `0063`) already existed — confirming a genuine mixed state (some schema silently created without a ledger row, some not) rather than a clean missing range. Also confirmed `0060`'s own `RunPython` effect was only *partially* applied: the `paid` plan's fields matched its intended values (not the raw column defaults), but the `free` plan's `feature_keys` was missing the key `0060` is supposed to add — a table/column existing is not evidence a `RunPython` migration's data effect actually ran; check the actual seeded values, every time, per migration.
