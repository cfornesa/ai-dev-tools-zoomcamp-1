# E2E full-matrix Firefox art-piece iframe timeouts

The curated Firefox subset's art-piece iframe tests can hit the 30s `testTimeout` in full-matrix CI while passing standalone and in chromium. Observed 2026-09-09 in the owner-triggered manual full-matrix run (`34404323033`, at current `main`, reflecting the current curated-subset config): all 3 firefox scenarios in `artPieceSteeringRuntime.spec.ts` failed at 30.3-30.4s.

**Correction:** an earlier version of this note cited a different run (`34307303394`) and claimed "9 other artPiece runtime tests" failed alongside it. That run predates both today's fixes and the firefox-curation change itself (`playwright.config.ts`'s firefox project now runs only `drawioEditor.spec.ts`, `artPieceSteeringRuntime.spec.ts`, and `manual2dStageChrome.spec.ts` — files like `artPieceFullZipRuntime`/`artPieceImmersive*`/`artPieceNonCameraZip` aren't even in the firefox project anymore). That evidence is stale and does not apply to the current config; independently re-verified against the actual current-`main` run, the only firefox failures are the 3 in `artPieceSteeringRuntime.spec.ts` — no other firefox test failed.

**Signature:** `waitForThreeJsReady` (line 138, waiting for `#art-piece-container canvas` inside the iframe) or `sendCommandAndAwaitPose` (line 332, waiting for a postMessage pose round-trip) timing out. The test that does NOT load a Three.js/A-Frame iframe (`hand steering controls are absent`) passes at 4.3s.

**Local reproduction failed:** the exact same 4 tests pass in ~14s standalone and under `--repeat-each=3` in firefox, even with other curated files interleaved.

**Classification (per #465's framework), stage 2b 2026-09-09:** (a) genuine Firefox-specific timing sensitivity, bounded to headless Linux CI's software-WebGL path — confirmed by instrumented evidence, not inference. In run `34404323033` the *identical* chromium scenarios passed in ~6.0s while firefox timed out at 30.3s *in the same run on the same runner*: this rules out (c) generic runner starvation, which would have slowed chromium proportionally. Locally, the full serial suite ran under a sustained all-core CPU stressor (load avg ~21-27 on 8 cores, 22.7 minutes) with temporary `[506]`-tagged probes on CDN request/response, iframe attach, and canvas creation; CDN responses arrived in ~64ms, iframes attached at ~600ms, and all 7 curated firefox tests passed, so ordinary load does not reproduce it either. macOS Firefox has GPU-backed (Metal) WebGL; the Linux CI runner's headless Firefox uses a software WebGL rasterizer, whose context initialization inside the opaque-origin sandboxed iframe can stall past 30s on a shared vCPU. It is not (b): the scenario's own work completes in seconds on every path where the sandbox actually initializes, in every browser.

**Resolution:** `artPieceSteeringRuntime.spec.ts` now sets a 90s timeout (3x headroom over the observed 30s stall) on exactly its three rendering scenarios, only when `test.info().project.name === 'firefox'` — chromium's default 30s and the no-rendering capability test (4.3s on CI) are untouched. No steering/pose assertion was weakened; only the wall-clock budget for headless-Firefox sandbox initialization grew. Actual CI confirmation is pending the next nightly full-matrix run (the stall only ever reproduced on the Linux CI runner); if the 90s firefox scenarios still stall there, suspect a real headless-Firefox software-WebGL deadlock rather than slowness and re-instrument with the `[506]` probe pattern from the 2b session rather than raising the timeout again.


**Not the same as #504/#505:** #504 is an fps-floor issue on the synthetic camera benchmark (chromium, independent of iframe loading). #505 is session/plan cross-test leakage (any browser, deterministic drift). #506 is a firefox-only iframe startup timing issue.

**Routing (resolved 2026-09-09):** stage 2b handled it as a scoped firefox-only timeout extension, not a runtime change — runtime investigation only becomes necessary if the 90s budget still stalls on CI (see above). The curated firefox subset was newly added to CI on 2026-09-09; this was previously-unknown, not a regression.
